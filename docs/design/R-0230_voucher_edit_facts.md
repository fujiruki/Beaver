## 1. 画面の入口と種類

- 【事実】ルートは2本、同じ `VoucherEdit`。`/vouchers/new`（新規）と `/vouchers/:id`（編集）。一覧は `/vouchers`（`App.tsx:48-50`）。実URLは `/contents/Beaver/` が前につく
- 【事実】新規か編集かは `id` の有無で決まる（`isNew = !id`、VE:269）
- 【事実】新規のときのURLクエリ: `type`（estimate/sales、既定 estimate）、`project_id`、`customer_id`（VE:271-274, 302-305）。案件を選ぶと、得意先が未設定なら案件の得意先を入れる（R-0148、VE:372付近）
- 【事実】見積と売上は同じ画面。違いは次の4点
  - 日付の項目名が「見積日」か「売上日」（VH:78）
  - 「有効期限」欄は見積のみ（VH:153）
  - 見積のみ「引用して売上」ボタン（VE:841）。引用済みの見積には、引用先の売上へのリンク帯が出る（VE:904）
  - 売上で見積から引用された伝票には、元の見積へのリンク帯が出る（VE:921）
- 【事実】読み取り専用の入口は2つ
  - `?readonly=1`（`isReadOnly`、VE:267）。トップバーに「参照モード」バッジ、「編集」ボタン（編集可能なとき）または「編集できません（理由）」、下部は「← 案件に戻る」のみ（VE:798, 831-838, 1015）
  - 伝票の状態で編集不可（`canEdit`、VE:`getVoucherEditBlockReason`）。編集可能な状態は draft・submitted・approved だけ。請求済み・取消・引用済み見積などは入力欄が無効になる。`void` のときは「取消を戻す」ボタン（`UnvoidVoucherButton`）が出る
- 【事実】Access由来の伝票: トップバーに「Access由来」（青）/「Beaver作成」（緑）バッジ、「Access№」、「最終同期」、「最終更新」（VE:803-828）。Accessで請求済み（`access_billed_flag=1`）なら赤帯「Accessで請求済み（請求日 …）のため編集できません」、`sync_pending=1` なら黄帯「Access で確認待ちです」（VE:888-902）
- 【事実】請求済み伝票でも案件のプルダウンだけは変更できる（`canEditLockedProject`、VE:`saveLockedProject`）
- 【事実】存在しないid（404）は「この伝票は見つかりません…」と「伝票一覧へ」リンクだけの画面（VE:737-743）

## 3. 保存の仕組み

### 3.1 新規
- 【事実】自動保存なし。「保存」で POST（ヘッダー）→ 明細を1行ずつ POST（`/vouchers/{id}/lines`）→ 作成した `/vouchers/{id}` へ遷移（VE:`onSubmit`）。途中で失敗しても作成済みidと保存済み行数を ref に持ち、再実行すると続きから（R-0119）
- 【事実】新規の未保存判定は `isDirty` のみ。離れるときの警告は 3.3

### 3.2 編集（R-0164）
- 【事実】ヘッダー: テキスト入力はフォーカスが外れたとき（`onBlurCapture`）、select・date・税トグルは変更した時点で保存（VE:`handleHeaderBlur/Change`）。date は blur では送らず change で送る。送る内容は `toHeader` の16項目すべて（変更分のみではない）
- 【事実】送る前に `customer_id`・`voucher_date` を検証。通らなければ送らず「未保存の変更があります」を出す
- 【事実】保存は直列キュー（`enqueueVoucherWrite`、`expected_updated_at` を付けて送る楽観ロック、R-0166）。ヘッダーは保存中に変更があれば最後の値だけ再送（`queuedHeaderRef`）
- 【事実】明細: 各入力欄の blur で、その行を PUT（`saveLineToDb`、LIR:130付近）。送る項目は品名・取付場所・行種別・数量・労務単価・金額・課税区分・備考・costs・prices。製品台帳の選択、「原価から売値を設定」、▲▼も即時PUT。行追加・複製・挿入はサーバーに先に作り、返ってきた行をフォーム末尾に足す。行削除は即DELETE（確認なし）
- 【事実】並べ替え: ▲▼は2行の `line_no` を2回PUT。挿入は選択行の「次」ではなく、サーバー側が末尾に作るため、フォーム上は末尾に足される（コメント VE:577付近「サーバーは行を末尾に作る」）【仮説】挿入位置は見た目でも末尾になる（コード上 `addLineOnServer` は `append`）

### 3.3 保存状態の表示とエラー
- 【事実】右下固定ボックス（編集のみ）: 「保存中…」「保存しました HH:MM」「未保存の変更があります」「保存に失敗しました: 理由 [再試行]」。404 は「この伝票は見つかりません」＋「伝票一覧へ」
- 【事実】409 stale_voucher: 赤い太枠の警告「ほかで更新されています（最終更新: …）。再読み込みすると、この画面で保存されていない入力は失われます。」＋「再読み込み」ボタン。以後の書き込みは止まる
- 【事実】トップに出るエラー: mutation の `mutError` が出ている場合は赤帯「保存に失敗しました: …」（状態表示とは別。新規保存失敗時に使われる）
- 【事実】離れるとき（R-0168）: 画面内遷移は `useBlocker` で捕捉し、確認ダイアログなしで未保存ヘッダーを保存し、保存中のものがすべて終わるのを待つ。成功なら移動、409や失敗なら移動せず上記表示。必須項目が空のときだけ `window.confirm('保存されていない変更があります。破棄して移動しますか？')`
- 【事実】タブを閉じる・再読み込み: `beforeunload`（ブラウザ標準の警告）。保存中・未保存・失敗・stale のとき
- 【事実】元に戻す（undo/redo）: この画面にはコードが無い。`docs/spec/R-0098_undo_redo.md` は存在する【未確認】他画面向けか、未実装かは読んでいない
- 【事実】確認ダイアログを使う操作: 引用して売上（`confirm`）、利益率バーの全行適用（`window.confirm`）、離脱時の破棄確認。行削除・台帳の紐付け解除には確認なし

## 4. キーボード操作・入力の工夫

- 【事実】この画面のコードに `onKeyDown`・Enter 処理・IME 判定（`isComposing`）・矢印キー処理は無い（grep済み）。Tab は標準のフォーカス移動のみ
- 【事実】`<form>` なので、テキスト入力で Enter を押すと標準の submit が働く。新規では「保存」と同じ処理が走る。編集では `onSubmit` がヘッダーを PUT して `closeGoBack()` する（VE:`onSubmit`）【仮説】編集時に Enter で画面が閉じる可能性がある（実機未確認）
- 【事実】早押しボタン: 利益率のプリセットボタン（PRB）だけ。ほかに数量や単価の早押しは無い
- 【事実】候補表示: `TateguSelector` の検索（部分一致）のみ。得意先・案件は素の select（検索なし）
- 【事実】数値欄はフォーカス中にカンマを入れない整形（入力中も3桁区切り表示、`formatNumber(parseNumber(raw))`）。IME 変換中の扱いは未確認
- 【事実】date 入力はブラウザ標準の date picker
