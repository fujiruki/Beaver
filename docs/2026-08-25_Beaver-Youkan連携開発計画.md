# Beaver × Youkan 連携開発計画

作成日: 2026-08-25  
対象: Beaver 開発AI  
状態: **開発引き継ぎ・設計方針。最終仕様書ではない**

> この文書だけを読んで即実装しないこと。Beaver の `SDDD.md`、`CLAUDE.md`、`docs/requests.md`、現行仕様を確認し、SdDD の要望登録→仕様化→タスク化の手順に従うこと。

---

## 0. 最初に結論：開発AIへ渡す順番

**最初は Beaver 開発AIに渡す。** ただし Beaver 側を最後まで作り切ってから Youkan に渡すのではない。

推奨順序は以下。

1. **Beaver B1**: 工数の正本・連携データ契約を固める。Youkanにはまだ依存しない
2. **Youkan Y1**: Beaver案件の受け口、未配置負荷、容量シミュレーションを作る
3. **Beaver B2**: Youkanへのpushと「この案件は入るか」の表示を接続する
4. **Beaver B3**: 見積内訳（作業パッケージ）を安全に外部公開する
5. **Youkan Y2**: 見積内訳→サブプロジェクト→実作業への段階分解を実装する
6. **Youkan Y3**: バッファ確認、仮配置、担当者別シミュレーション等を追加する

**Beaver AIは B1 が終わった時点で一度止まり、契約内容を明文化して Youkan AIへ渡すこと。**

理由: Beaver は案件・見積工数の正本、Youkan は実行計画・キャパシティの正本であり、Youkan側の受け口が決まる前に Beaver から直接呼び出す実装を先に作ると、両システムが密結合になるため。

---

# 1. この連携で解決したいこと

案件は時間が経つにつれて工数の解像度が上がる。

### 段階1: 案件登録

「この案件、たぶん全部で 20h くらいかかる」

- 入力場所: Beaver 案件
- まだ見積明細はない
- それでも Youkan の将来負荷には 20h として影響させたい

### 段階2: 見積作成・編集

「製作 12h、取付 3h、その他 5h」など、項目別工数が分かってくる。

- 入力場所: Beaver 見積
- 段階1の20hへ単純加算してはならない
- 20hという粗い見積を、より細かい内訳へ置き換えていく

### 段階3: 受注後の実行計画

「製作12h」を Youkan 側で、

- 木取り 3h
- 分決め 2h
- 加工 4h
- 仕上げ 1h
- 残り未分解 2h

のように分解し、担当・日付・依存関係を詰める。

**重要:** 段階1・2でも、Youkanのスケジュールや空き容量判定へ必ず影響させる。詳細化されていない仕事を「予定にないから存在しない」扱いにしない。

# 2. システム責務

## Beaver が正本

- 案件ID / 案件コード
- 案件名
- 得意先・現場情報
- 案件ステータス
- 納期
- 案件登録時の概算工数
- 見積書上の工数・工数内訳
- 商業上の見積基準値

## Youkan が正本

- 実行用プロジェクト階層
- サブプロジェクト / タスク分解
- 担当者
- 依存関係
- いつやるか
- 未配置負荷
- バッファ
- キャパシティ判定
- focus / 実行状態

## 禁止

- Youkanで案件名を変更した結果をBeaverへ逆同期しない
- Youkanのタスク分解をBeaverの見積明細へ書き戻さない
- 案件名で同期対象を照合しない
- BeaverがYoukan側で追加された子タスクを削除・上書きしない
- 同期失敗時に案件登録そのものを失敗させない

---

# 3. 現在の Beaver に既にあるもの

現行コードには、少なくとも以下が存在する。

- `projects.manual_estimated_hours`
- 案件作成・更新時の `manual_estimated_hours` 入出力
- 見積伝票明細の `cost_factory_hours × quantity`
- 見積伝票明細の `cost_site_hours × quantity`
- 見積工数が存在すればそれを優先し、なければ `manual_estimated_hours` を使う `effective_estimated_hours`
- `GET /projects/sync` という既存の AccessTategu 向け同期API

したがって、**「案件登録時にたぶんX時間」を入力する機能をゼロから再実装しないこと。** 現状UI・API・DBが要求を満たしているかをまず確認し、不足だけ直す。

---

# 4. B1: Beaver側で最初にやること

## 4.1 目的

Youkanが安心して読める「案件工数の外部契約」を作る。

B1では、BeaverからYoukanを直接呼ばない。まず **Beaver単体で完結する読み取り契約** を完成させる。

## 4.2 既存 `/projects/sync` を安易に流用しない

現行 `/projects/sync` は AccessTategu 用の契約として既に使用されている。

Youkan向けに必要な情報・更新頻度・意味が異なるため、原則として専用の連携APIまたは明確にバージョン分離した契約を設ける。

例（名前は仕様化時に決定）:

```text
GET /integrations/youkan/projects
GET /integrations/youkan/projects/{id}
```

既存 Access 契約を壊さないことを優先する。

## 4.3 B1で外部公開したい最小データ

概念上、以下を返せればよい。

```json
{
  "source": "beaver",
  "external_project_id": 123,
  "project_code": "P00123",
  "name": "○○様邸 建具工事",
  "customer_name": "○○様",
  "status": "受注済",
  "delivery_date": "2026-09-10",
  "baseline_hours": 20.0,
  "baseline_source": "manual",
  "baseline_updated_at": "2026-08-25T09:00:00+09:00",
  "updated_at": "2026-08-25T09:00:00+09:00"
}
```

`baseline_source` は少なくとも以下を区別する。

- `manual`: 案件登録時の概算
- `estimate`: 見積明細から算出

ユーザーに「確度」を入力させない。どこから算出したかで自動決定する。

---

# 5. 重要な設計ゲート：複数見積の正本

現行 `effective_estimated_hours` の算出ロジックは、プロジェクトに紐づく `voucher_type = estimate` かつ `status != void` の明細を集計する。

**Youkan連携前に必ず、1案件に複数の有効見積が存在する場合の意味を調査すること。**

例:

- 初回見積 20h
- 改訂見積 22h

を両方足して42hとしてはいけない。

B1で以下のどれを正本にするか仕様化する。

候補:

1. 明示的な「計画基準見積」を案件に1件指定する
2. approved の最新1件を優先する
3. approved がなければ最新の非void見積1件を使う

**既存データの実態を確認せず、ここを推測で決めない。**

Youkanへ渡す `baseline_hours` は、常に「現在この案件を何時間案件として扱うべきか」を1値で返すこと。

---

# 6. B1 の終了条件

以下が満たされたら、Beaver AIは一度止まり Youkan AIへ渡す。

- [ ] 案件登録時概算工数の現状を確認済み
- [ ] 見積が無い時は手動工数、見積がある時は見積基準へ移行できる
- [ ] 複数見積時の正本が仕様化されている
- [ ] Youkan向け最小案件工数APIがある
- [ ] stableな `external_project_id` と `project_code` を返す
- [ ] `baseline_source` を返す
- [ ] キャンセル案件・完了案件の扱いを契約に明記する
- [ ] AccessTategu既存連携を壊していない
- [ ] API契約とサンプルレスポンスを Beaver の仕様書へ残した

この時点では以下を作らなくてよい。

- Youkanへのpush
- 空き容量表示
- 自動スケジュール
- 見積内訳のサブプロジェクト同期
- バッファUI

# 7. Youkan Y1 完了後に Beaver へ戻って B2

Youkan側で以下が完成してから着手する。

- Beaver案件IDとYoukanプロジェクトの一意リンク
- Beaver由来の概算工数を未配置負荷として扱える
- 納期までの容量シミュレーションAPI
- 二重計上しない負荷計算

## B2で行うこと

### 7.1 Beaver保存後のpush

最終的には以下の流れ。

```text
Beaverで案件保存
  ↓
Beaver backend
  ↓
Youkan integration APIへupsert
  ↓
Youkan側で藤田建具店テナントの対応プロジェクトを更新
```

ブラウザから直接Youkanを呼ばない。backend-to-backend とする。

push失敗時:

- Beaverの案件保存は成功させる
- 同期失敗状態を記録する
- 再同期できる

定期・手動syncを保険として残し、push一本足にしない。

### 7.2 Beaverに容量結果を表示

案件詳細・案件一覧では、Youkanが返した結果を読み取り専用で表示する。

例:

```text
工数        20h（概算）
バッファ込み 24h
納期        9/10

Youkan判定: 入る
予測完了:    9/7
残余力:      4h
```

または

```text
Youkan判定: 入らない
不足:        6h
```

Beaver自身がキャパシティ計算ロジックを持たない。**容量判定はYoukanを正本とする。**

# 8. B3: 見積工数を「作業パッケージ」として公開

B2まで動いてから行う。

段階2では総工数だけでなく、見積の各項目を Youkan でサブプロジェクト化できるようにしたい。

例:

```text
案件A 20h
├ 製作 12h
├ 取付 3h
└ その他 5h
```

## 外部契約イメージ

```json
{
  "baseline_hours": 20,
  "baseline_source": "estimate",
  "work_packages": [
    {
      "external_work_key": "voucher:55:line:101",
      "label": "製作",
      "baseline_hours": 12
    },
    {
      "external_work_key": "voucher:55:line:102",
      "label": "取付",
      "baseline_hours": 3
    }
  ]
}
```

実際に「伝票行単位」「集計区分単位」「製作/施工の2分類」など、どの粒度が利用者に自然かは現行見積データを調査して仕様化する。

## stable key

同期はラベルではなくIDで行う。

見積行を削除→新規作成した場合など、upstream IDが変わるケースでは、Youkan側の既存分解を勝手に消さない。

Youkanでは削除元パッケージを「Beaver側から消えたので要確認」とできる設計にする。

---

# 9. 粗い工数→詳細工数の意味

Beaver側の基準工数は、Youkanで詳細化されても書き換えない。

例:

```text
Beaver見積
製作 5h
```

Youkanで

```text
製作 5h
├ 木取り 2h
├ 分決め 2h
└ 仕上げ 2h
```

となり6h必要と判明しても、Beaverの見積5hは過去予測として保持する。

Youkan側では

```text
基準工数 5h
現在計画 6h
差       +1h
```

と扱う。

**Youkanの計画超過をBeaver見積へ自動反映しない。** 必要なら将来「参考表示」だけ返す。

---

# 10. テンプレート機能の責務

「見積」「打ち合わせ」「発注」「請求処理」などの実行タスクテンプレートは、基本的にYoukan側の責務とする。

Beaverの案件ステータス変更をイベントとして利用するのはよい。

例:

- 問い合わせ → 現調・打ち合わせ・見積候補
- 受注済 → 発注・製作・取付の確認
- 納品済 → 請求処理

ただし、案件作成時に全テンプレートタスクを一括生成してタスクを増やさない。

Beaver側は「状態」を提供し、Youkan側が必要な時点で提案・生成する。

---

# 11. ユーザー負担を増やさない設計原則

この連携では以下を守る。

1. **粗い入力でも即役に立つ**
   - 案件登録時は「20hくらい」だけでよい
2. **詳しくした分だけ精度が上がる**
   - 詳細化を必須にしない
3. **同じ情報をBeaverとYoukanへ二重入力させない**
4. **工数の由来は自動判定する**
   - 概算/見積/実行計画をユーザーに選ばせない
5. **Beaver画面では結論を見せる**
   - ガントを見て自分で計算させない
6. **警告は例外時だけ**
   - 通常同期成功を毎回通知しない

---

# 12. 非機能要件

## 冪等性

同じ Beaver project ID を何度送っても Youkan プロジェクトが増殖しないこと。

## 認証

- backend-to-backend 用認証
- テナント名「藤田建具店」を文字列ハードコードしない
- Youkanのtenant IDまたは連携設定で紐付ける

## 障害分離

Youkan停止中でもBeaverで案件・見積を登録できる。

## 監査

最低限、以下を追えるようにする。

- 最終同期時刻
- 最終同期結果
- Beaver側更新時刻
- Youkan側で最後に受けたsource version

---

# 13. 開発AIが次AIへ渡すもの

B1完了時、Beaver AIは少なくとも以下を明文化すること。

```text
1. Youkanが呼ぶURL
2. 認証方式
3. project IDの型
4. baseline_hoursの算出ルール
5. baseline_sourceの値域
6. 複数見積の正本ルール
7. statusの値域
8. delivery_dateの意味
9. updated_after等の差分同期方法
10. サンプルJSON
```

Youkan AIに「コードを読めば分かる」と渡さない。

---

# 14. 最終的に目指すUX

案件登録時:

```text
たぶん 20h
↓
「現在の仕事量なら、この納期までに入る」
```

見積後:

```text
当初 20h
見積 24h
↓
「バッファ込みでは3h不足」
```

受注・詳細計画後:

```text
製作 16h
├ 木取り 3h  8/28
├ 加工   5h  8/29
├ 組立   4h  9/1
└ 未分解 4h

↓
「9/2頃まで実質埋まっている」
```

**連携の目的は「Beaverの案件をYoukanにもコピーすること」ではない。**

目的は、

> Beaverで受けた仕事を、情報が粗い段階からYoukanが仕事量として認識し、現在の予定・未配置仕事・キャパシティを踏まえて「受けられるか」「いつ頃まで埋まっているか」を答えられるようにすること。

である。
