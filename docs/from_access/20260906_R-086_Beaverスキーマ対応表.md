## 2. AccessとのID対応

### 2.1 得意先ID —— **共通IDではない（別ID＋マッピング列）**

結論: Accessの`tbl得意先M.得意先№`とBeaverの`customers.id`は**別々に採番される独立したID**であり、`customers.access_customer_no`（TEXT, UNIQUE）でマッピングしている。

根拠:
1. `customers.id` は `INTEGER PRIMARY KEY AUTOINCREMENT`（`Beaver/api/schema.sql:47`）。Accessの`得意先№`は`INTEGER NOT NULL PRIMARY KEY`で通常Long列（`src/migrations/001_initial_schema.sql:65`）
2. migration 009:2-3「AccessTategu の tbl得意先M.得意先番号（LONG）を文字列保持する。既存得意先は NULL のまま運用、晴樹さんが必要時に手動で紐付ける想定」→ 設計時点から「別ID＋紐付け」方式
3. Access→Beaver payloadは`access_customer_no`=`CStr(得意先№)`を送る（`Df_Beaver連携Push.bas:521-524`）。Beaverは`access_customer_no`で既存行を検索して更新、無ければ`code`でフォールバック照合、それも無ければ新規INSERT（`customers.php:266-312, 325-360`）
4. 伝票push時は`customer_access_no`→`customers.id`を`resolveCustomerId`で解決して`vouchers.customer_id`に入れる（`sync_helpers.php:81-87, 185-193`）。`vouchers.customer_id`にAccessの`得意先№`が直接入ることはない
5. Beaver発の新規得意先は`code`を90001〜で採番し、`access_customer_no`はNULL（`customers.php:163-176`）。Access取込時に`access_customer_no`が数値かつ未使用ならそれを`得意先№`に採用、無ければ`DMax(得意先№)+1`で採番（`Df_Beaver連携.bas:3302-3319`）
6. `Df_Beaver連携.bas:2197`のコメント「得意先の Access-Beaver リンクキーは access_customer_no（= tbl得意先M.得意先№）」

指揮役の決定（得意先は両システムが正本、更新日時の新しい方を採用、共通IDであるべき）との**差分**:
- 現状は「`customers.id`（Beaver内部）」と「`得意先№`（Access）」の2つのIDが並存し、`access_customer_no`が橋渡し
- Beaver発得意先の`code`（90001〜）はAccess取込後に`得意先№`として採用される（`Df_Beaver連携.bas:3307-3313`）ため、実運用では「`code` = `access_customer_no` = `得意先№`」が成り立つよう寄せられている（`customers.php:314-316`の「晴樹さん方針: Beaverのcodeを常にAccessの得意先番号と一致させる」）。ただし`customers.id`自体は依然として別値で、`vouchers.customer_id`/`projects.customer_id`はこの内部IDを参照している
- Dodaikunで真に共通IDにするなら、(a) Beaverの`customers.id`をAccess側`得意先№`に合わせて振り直す（FK付け替えを伴う大移行）か、(b) `code`/`access_customer_no`を実質的な共通キーと位置づけ`customers.id`は内部実装として隠蔽する、のどちらかを決める必要がある。（推測: 現状の構造からは(b)が現実的）

### 2.2 案件ID —— **共通ID**

Accessの`tbl案件_cache.案件番号`/`tbl見積.案件番号`/`tbl売上.案件番号`は、Beaverの`projects.id`をそのまま保持している。

根拠:

| # | 項目 | 内容 | 根拠 |
|---|---|---|---|
| D-1 | 伝票IDの衝突リスク | `vouchers.access_voucher_id`は単独UNIQUE。Accessの見積№と売上№は別採番のため、同番号が存在すると片方がupsertで**上書き**される（`ON CONFLICT(access_voucher_id) DO UPDATE`で`voucher_type`も書き換わる）。Dodaikun統合で1採番になれば解消するが、既存Beaverデータの再紐付けが必要 | migration 011:8-9, `sync_helpers.php:321-322` |

| D-3 | 案件IDは共通 | §2.2参照。Dodaikunでもこの方式を踏襲すればよい | |
| D-4 | `total_amount`の意味不一致 | Beaver内部（`recalcVoucher`）は税込合計、Accessからは`DSum(明細金額)`＝税抜合計を送っている。Beaver側で`recalcVoucher`が走ると（UI編集時）値が税込に置き換わり、Access側と食い違う | `vouchers.php:281`, `Push.bas:163` |

| D-6 | `voucher_lines.source`のDEFAULT | Beaver UIで追加した明細も`source='access'`になる（DEFAULT）。出自判定には`edited_in_beaver`しか信用できない | migration 016:1, `vouchers.php:778-782` |
