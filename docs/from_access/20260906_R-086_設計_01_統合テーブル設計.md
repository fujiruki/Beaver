### 1-3. 設計の前提（既決事項、requests.md:104-147 より。本書では変更しない）

1. 見積・売上を1テーブルに統合し `voucher_type` で区別。値はBeaverと同じ `'estimate'` / `'sales'`（対応表D-11）
2. 見積→売上は「見積を残したまま売上レコードを複製し `source_estimate_id` でリンク」方式（requests.md:133）
3. 伝票№は統合後**1採番**（R-093の根治、requests.md:183）
4. コード上の名前は英語、UI表示名は日本語（requests.md:104）
5. 得意先IDは `得意先№` を共通キーとする（設計書3）。案件IDは `案件番号` ＝ `projects.id`（対応表§2.2）
6. 値引（`内訳="値引"`）は当面使用しない運用だが、過去データには存在する（`tbl売上明細` 832件・`tbl見積明細` 61件、R-087§1）

### 2-4. 種別固有列の持ち方【提案】共通列としてNULL許容（拡張テーブルは作らない）

**【事実】** 見積のみ: `引用日`・`税抜額印字`・`社印押印`・`有効期限`・`Excelファイル名`。売上のみ: `納品日`・`締日`・`見積伝票№`・`請求日`・`請求済`・`売掛ID`・`売上合計税込`・`事業者`・`ExcelファイルURL`・`粗利`（棚卸し§4-1）。全てスカラー値で、1伝票に1値。

| 案 | 内容 | 評価 |
|---|---|---|
| (a) 共通列・NULL許容 **推奨** | 全列を `vouchers` に持ち、種別に無関係な列はNULL | Beaverと同じ形（対応表§1.3は全て1テーブル）。フォームのRecordSourceが単一テーブル（またはその単純クエリ）になり更新可能性の問題が出ない。列数は33で001の `tbl売上`（24列）より9列多いだけ |
| (b) 種別ごとの拡張テーブル（`voucher_sales_ext` 等） | 共通列だけ `vouchers`、種別固有は1:1の子テーブル | JOINが常に必要になり、フォーム更新時に1:1結合の更新可能性・新規行の子行生成が問題化。R-086の動機（「同じ機能を二度作る」の解消）に逆行 |

BIT列（`print_tax_excl_flag`・`print_company_seal`・`billed_flag` 等）はJetでNULLを持てない（`docs/spec/04_データ設計.md:75`）ため、種別に無関係でも既定値 False を入れる。

### 2-5. 単価の持ち方【要決定 U-06】3列（本体/金物/ガラス）＋`line_total` を推奨

**【事実】**
- `Set本体金額`（`frm見積.frm:4462-4478`、コードベース地図§2-4）は原価3区分それぞれに `ROUND2(原価 ÷ (1-利益率))` を適用して3列を別々に決める。合算1列だと原価区分ごとの価格設定ができない
- R-091（税込/税抜切替）は「本体金額・金物金額・ガラス金額、または単価」が対象（requests.md:166）。3列のまま持てば「税込入力→3列に按分」の設計余地が残る
- Beaverも `price_body/price_hardware/price_glass` ＋ `line_total`（対応表§1.4）。同期の写像が1:1
- `qry見積サブ.sql:1` / `qry売上サブ.sql:1` は `単価 = 本体金額+金物金額+ガラス金額` をクエリ層で算出しており、1列にすると既存の `粗利`・`粗利率` 式の入力が変わる

| 案 | 評価 |
|---|---|
| (a) 3列＋`line_total`（現状踏襲）**推奨** | 情報損失なし。既存計算式・フォーム・Beaver写像を変えない |
| (b) `unit_price` 1列に合算 | 原価区分ごとの価格設定（`Set本体金額`）が成立しない。過去データの内訳が失われ、戻せない |

### 2-6. 原価6列と作業時間【提案】現状踏襲、`cost_site_hours` は作らない

- 6列（`cost_body/cost_hardware/cost_glass/cost_labor_rate`・`work_hours`）は旧列を1:1で持ち越す
- Beaverの `cost_site_hours`（現場作業時間）はAccessに対応列が無く（対応表§5.3）、追加は用途が決まってから。Jet の `ALTER TABLE ADD COLUMN` で後付け可能（§2-9参照）

### 2-7. 計算列はテーブルに持たずクエリ層で算出【提案】現状方針踏襲

**【事実】**
- 課税小計・非課税小計・値引小計・材料原価・労務費・製造原価・単価・粗利・純利益・粗利率・日割粗利は `qry見積サブ.sql:1` / `qry売上サブ.sql:1` の計算列であり、テーブル列ではない
- 2クエリの差分: `qry見積サブ` は `材料原価小計` を持ち `純利益`・`粗利率`・`日割粗利` を持たない。`qry売上サブ` はその逆。`qry見積サブ` は `Nz()` で原価NULLを0扱い、`qry売上サブ` は `Nz()` なし（NULL原価があると `粗利` がNULLになる）

- テーブルに持つキャッシュは `total_amount` のみ（§2-8）

## 6. 同期テーブルへの影響

### 6-1. `tbl同期キュー`【事実＋提案】

- **事実**: `対象テーブル` TEXT(50) に `'tbl見積'`/`'tbl売上'`、`対象ID` LONG に伝票№、`ペイロードJSON` に `access_voucher_id`＝伝票№ を含むJSONが入る（014:3-6、`Df_Beaver連携Push.bas:174-192`）。`EnqueueVoucherUpdateFromTable` は `対象テーブル` で `voucher_type`・明細テーブル・FK列を決める（`Push.bas:134-147`）
- **提案**:
  1. 移行の前提条件: `状態='pending'` または再試行対象の行が **0件** であること（ペイロード内の旧番号を書き換えるより、送り切ってから移行する方が確実）
  2. 履歴行（送信済み・失敗確定）は**書き換えない**（`対象テーブル='tbl見積'`・旧 `対象ID` のまま監査履歴として残す）
  3. 統合後の新規行は `対象テーブル='vouchers'`、`対象ID=vouchers.id`。種別はペイロードの `voucher_type` で判別する（列は増やさない）
  4. `PushReportTargetType`（`Push.bas:678-681`）等の表示は `'vouchers'` に対応させる

### 6-2. `tbl競合待ち`【事実＋提案】

- **事実**: `伝票種別` TEXT(10) に `'見積'`/`'売上'`、`伝票番号`・`access_voucher_id` LONG に伝票№、`Beaver伝票ID` に `vouchers.id`（Beaver内部ID）が入る（017:5-8）。`ApplyBeaverAdoptionCore`・`ApplyAccessAdoption` は `伝票種別` で対象テーブルを決める（`Df_Beaver連携.bas:2863-2867, 3866-3870`）
