### 2-2. `tbl得意先M` の列設計【要決定 C-01】

U-01 の帰結として `得意先№` をオートナンバー化するかどうか。既存 795 件の番号は据え置き。

| 案 | 内容 | 利点 | 欠点・条件 |
|---|---|---|---|
| (a) COUNTER 化 | `ALTER TABLE [tbl得意先M] ALTER COLUMN [得意先№] COUNTER(807,1)`（migration）。`frm得意先M.frm:1396` と `Df_Beaver連携.bas:3318` の採番代入を削除 | 伝票（U-01 (a)）と同方式。採番コードが消える | **データが入った PK 列の COUNTER 化が Jet で可能かは未実証**（設計書2 §3 の J-02 は空テーブルの seed 設定）。ベータで J-09 として実証が必要。COUNTER は明示値 INSERT（テスト行 99140、F-14）を受けると次番号が 99141 に飛ぶため、テスト側の番号域変更（§7）が前提 |

### 2-3. Beaver 発得意先の取込フロー（新）【提案】

```
Beaver UI で得意先作成（id=B、code=90001、access_customer_no=NULL）
  → GET /customers/sync で Access が受信（ProcessCustomerFromBeaver :2198）
  → tbl競合待ち に 種別 'new' / 伝票種別 '得意先' / Beaver伝票ID=B で pending
  → 晴樹さんが frm競合解決 で「Beaver採用」
  → ApplyBeaverAdoptionCore :2878-2902
       ① NextCustomerNo()（または COUNTER）で 得意先№=N を発行し INSERT
       ② CommitTrans
       ③ PATCH /customers/B/access-link {access_customer_no:"N", access_customer_code:"N"}   ← 新
          失敗時は tbl競合待ち.access_link_pending=True を残し次回同期で再送（R-081 B と同じ）
```

Beaver 側は `access-link` 受信で `access_customer_no=N`、`code=N`、`last_synced_at=updated_at=CURRENT_TIMESTAMP` を 1 UPDATE で行う。`code` の UNIQUE 違反（既に `code=N` の行がある＝過去の F-07 重複）は 409 で返し、Access 側は `適用警告ログ` に残す。

## 3. 突合・マージ支援機能

### 3-1. 入力と Beaver データの取得【要決定 C-02】

入力は Access 全得意先（`tbl得意先M` 795 件）× Beaver 全得意先（`customers` 全件、`is_active=0` も含む）。

| 案 | 取得手段 | 利点 | 欠点 |
|---|---|---|---|
| (a) API 直接 | 判定のたびに `GET /customers/sync`（`updated_after` 無し）を Access から呼ぶ | 実装済みの `BuildCustomerSyncUrl`（`:710`）を流用 | ベータ FE は `localhost:8003` に向く（設計書2 M-07）ため本番 Beaver の得意先を読めない。再現性が無い（毎回結果が変わりうる） |
| (b) JSON スナップショット → 取込テーブル | PowerShell `scripts/r086_fetch_beaver_customers.ps1 -Prod` が `GET /customers/sync` を全ページ取得し `beta/customer_match/beaver_customers_YYYYMMDD_HHmm.json` に保存（`initial_push_to_beaver.ps1:26-40` の `-Prod` 明示と同じ流儀）。Access の「Beaver を取込」ボタンがこのファイルを `beaver_customers_snapshot` テーブルに読み込む | ベータでも本番でも同じ入力で判定でき、再現・テスト可能。R-094 の「ファイル受け渡し」（requests.md:194 ②）の原型になる。個人情報は `beta/`（git 管理外）に置く | 鮮度は取得時点。適用前に再取得して `updated_at` 差分を検査する手順が必要（§3-7） |
| (c) SQLite コピー | `api/database.sqlite` を取得して Access から ODBC/ADO で読む | 全列そのまま | SQLite ODBC ドライバの導入が必要。本番 DB の持ち出し |

### 3-3. 判定ティア

決定論的ルールを先に適用し、AI 支援は T4 の補助に限る。判定は Access 行 A と Beaver 行 B の**全組合せ**（795 × Beaver 件数。数千〜数十万組、VBA でも数秒〜数十秒。`NormName` は前計算して配列に持つ）。

**スコア（組ごと、加点方式）**

| 一致項目 | 条件 | 点 |
|---|---|---|
| 名前完全一致 | `NormName(名前) = NormName(name)`、かつ空でない | 100 |
| カナ完全一致 | `NormKana(名前カナ) = NormKana(name_kana)`、かつ空でない | 60 |
| 電話一致 | `NormTel` が 3×3 のいずれかで一致 | 50 |
| メール一致 | `LCase(Trim(電子メール)) = LCase(Trim(email))`、空でない | 50 |
| 名前包含 | `NameContains` | 40 |
| 名前類似 | `NameSim >= 0.8`（包含と重複加点しない） | 30 |
| 住所一致 | `NormAddr(住所１) = NormAddr(address1)`、空でない | 30 |
| 郵便番号一致 | `NormPostal` 一致 | 20 |

**除外**: Access 側の `名前` が `得意先NNN`（`Df_Beaver連携.bas:3325` のプレースホルダ）の行は名前系の加点を行わない。`使用不可=True`／`is_active=0` は判定から除外せず `match_keys` に `inactive` を付記する。

**ティア**

| ティア | 名称 | 判定式 | 扱い |
|---|---|---|---|
| T1 | 紐付き済み | `B.access_customer_no` が数値で `A.得意先№` と等しい行が存在 | 一覧表示のうえ**一括承認**（実質確認のみ）。`B.code <> B.access_customer_no` の行は `match_keys='code_mismatch'` を付け、適用で `code` を揃える。`access_customer_no` が数値だが Access に存在しない B は **T1x（孤児リンク）** として T4 扱い |
| T2 | 正規化名の完全一致 | 名前完全一致（100 点）かつ **A から見て B が唯一、B から見て A が唯一**（1 対 1） | 一覧表示のうえ一括承認 |
| T3 | 強キー一致 | T2 でなく、(電話一致 OR メール一致) AND (カナ一致 OR 郵便番号一致 OR 住所一致 OR 名前包含 OR 名前類似)、または (郵便番号一致 AND 住所一致 AND (カナ一致 OR 名前包含 OR 名前類似))。かつ 1 対 1 | 一覧表示のうえ一括承認【要決定 C-04】 |
| T4 | 怪しい | スコア >= 30 で T2/T3 に該当しない組。名前完全一致でも 1 対 1 でない組（同名複数）。T1x | **1 件ずつ質問**。AI 所見の対象 |
| T5 | 片方にしか無い | T1〜T4 のどの組にも現れない A（Access のみ）／B（Beaver のみ） | 「相手側に作成」を一括承認。T4 の「別」判定で相手が無くなった行は再判定で T5 に落ちる（§3-7） |
| T6 | Beaver 内重複 | 同じ A に対し T1 の B1 と T2/T3 の B2 が両方存在（F-07 で生まれた重複の典型） | 一覧表示。B2 の `projects`/`vouchers`/`invoices`/`payments` を B1 に付け替えて B2 を無効化する **Beaver 側作業**（§4-6）【要決定 C-10】 |
| T7 | Access 内重複 | `NormName` が同じ A が複数 | **報告のみ**（本機能では統合しない）【要決定 C-09】 |

1 対 1 の判定は「スコア最上位の相手が互いに相手である（相互最良）」で行う。同点は T4 に落とす。

既存の `ResolvePastCustomerLink`（F-08）との関係: 同関数は同期中の 1 件ずつの判定用で、名前は完全一致（正規化なし）。本機能の `NormName` ベースの判定に統一するため、P4 で `ResolvePastCustomerLink` の比較を `Dodaikun_CustomerMatch` の関数に置き換える【提案】（`Test_R084` の期待値は変えない: 完全一致は正規化後も一致する）。
