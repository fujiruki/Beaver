# ADR-0001: 木材原価の部位と明細を Access と同じ表で両方向に同期し、TateDS の建具データも同期する

- 状態: 採用
- 日付: 2026-11-13
- 関連要望: R-0268（仕様 `docs/spec/R-0268_wood_cost.md`）。R-0200 の「木材設定・木材明細は Access だけ」を置き換える

## 背景

- 木材原価（部位ごとの樹種・立米単価と、用途・寸法・本数の明細）は Access だけにあり、Beaver には計算結果の原価行（`wood_calc`）しか来ない
- 晴樹さんは Beaver でも木材を入力したい。将来は建具デザインスタジオ（TateDS）の材料リストを流し込み、その建具を開けるようにしたい
- 伝票と製品台帳は Access と Beaver の両方で直され、両方向に同期している（R-0200、競合の単位は台帳1件、競合は Access の承認画面で選ぶ）
- TateDS にはサーバーが無く、建具データは各ブラウザの中にある

## 比較した選択肢

| 案 | 概要 | 長所 | 短所 |
|:--|:--|:--|:--|
| A | 木材は Access だけ（今のまま） | 作る量が無い | Beaver で入力できない。TateDS とつなげない |
| B | Beaver と Access で別の形の表、結果だけ同期 | 各側で自由に作れる | Access で直すと Beaver の明細・建具データとずれる |
| C | Access と1対1の表で両方向に同期。建具データも同期 | どちらで直しても同じ。TateDS で開くのも両方でできる | Access 側の改修が要る。同期の決まりが増える |

## 決定

案 C。主な決まり:

1. 部位は作った側が振る `uid` で突き合わせる。明細は部位ごとに全件入れ替え
2. 部位に合計 `amount`（整数円）を持たせて運び、受け取った側は計算し直さない。丸めは両側とも四捨五入
3. 原価行の数量は人が決める値（枚数）。部位から作り直しても数量は触らない
4. 建具データ（JSON）は台帳に1つ、製品図と同じく別の口（multipart）で運び、台帳の同期にはハッシュだけ載せる
5. 製品台帳の書き込みに楽観ロック（409 `stale_product`）
6. 樹種表は Access → Beaver の片方向
7. 「TateDS で開く」は Beaver・Access 共通で「クリップボードに建具データ → TateDS で貼り付けて開く」
8. 入れ替えの順: Beaver（受け取れるようにするだけ）→ Access → Beaver の編集を開ける

## 理由

- 晴樹さんの判断「Beaver と Access はほぼ同じ DB であるべき」。案 B では Access で直した明細と建具データが Beaver でずれる
- 1〜6 はアドバイザ2人の検討（`docs/wiki/knowledge/R-0268_review_sync.md`・`R-0268_review_ux.md`）で、案 C を素直に作ると起きる問題への対策: オートナンバーの ID が同期のたびに変わる、通貨型と整数の丸めの差で1円ずつ往復する、数量1固定で枚数を使う原価が減る、大きな JSON が WAF の403と Access の SQL 文の上限に当たる、自動保存で Access の変更を黙って上書きする
- 7 は Access が開いたタブへ直接データを渡せないため、両側を同じ作りにそろえた

## トレードオフ

- Access 側（dodai-back）に表の列追加・同期・承認画面・複製・丸めの改修が要り、Beaver だけでは完了しない
- 合計を運ぶため、明細と合計が食い違った状態も同期される（人が直したときだけ計算し直す）。既存の19行は差を表示して残す
- 建具データの控えが DB に入り、台帳1件あたりのデータが大きくなる

## 見直す条件

- TateDS がサーバーと建具ごとの URL を持ったら、建具データの控えをやめてリンクだけにする
- Access を使わなくなったら、同期の決まり（uid・amount の運搬・樹種表の片方向）を見直す
