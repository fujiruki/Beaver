## (a) 子の表（部位・明細）の ID の対応付け

### 指摘2【高】オートナンバーの対応付けは、全件入れ替えのたびに壊れる

根拠:
- Beaver は台帳の子を全件入れ替えている。`replaceTateguSyncLines` は `DELETE FROM tategu_item_cost_lines WHERE tategu_item_id = ?` のあとで入れ直す（`api/routes/tategu_items.php:75-85`）。このため、原価行の ID は Access から届くたびに変わる
- Access も Beaver から取り込むときに全件入れ替えている。`ApplyBeaverProduct` は本体・金物・硝子・労務を DELETE してから INSERT する（`Df_製品台帳同期.bas:1121-1124`）。オートナンバーの ID も取り込むたびに変わる
- 案は部位・明細に `id / access_id` を持たせ、原価行には `wood_set_id`、Access の本体行には `木材設定ID` で部位を指させる（R-0268 の「表」と「原価の行とのつながり」）。片方で入れ替えると、もう片方の ID と、それを指す行（原価行の wood_set_id、本体の木材設定ID）を毎回付け替えることになる
- 部位を Beaver で作った場合、Access の ID を Beaver に書き戻す口が要る。今の access-link が受け取るのは `code` だけ（`tategu_items.php:185-194`）。伝票には明細ごとに `access_line_id` を持たせ、その値をキーに入れ替える仕組み（`sync_helpers.php:742-770` の `upsertSyncedLines`）があるが、台帳の子にはこの仕組みが無い
- Access の木材画面は、隠し欄 `txtMokuzaiSettingId` に設定IDを持つ（調査 §2）。開いている間に取り込みで設定を入れ替えると、ID が指す行が消え、そのあとの入力は孤立した設定IDに付く

直し方:
- 部位（tategu_wood_sets・tbl建具台帳_木材設定）に、作った側が振る `uid`（UUID の文字列）を足す。両側とも `uid` で突き合わせて追加・更新・削除する（upsert）。オートナンバーは各側の中だけで使い、相手の ID は持たない。`access_id` 列は要らない
- 原価行の `wood_set_id` と Access 本体行の `木材設定ID` の付け替えは、同期の中では `uid` を通して行う。同期の JSON では、wood_calc の原価行に `wood_set_uid` を付ける（今の `AppendCostLines` は `source` しか送っていない。`Df_製品台帳同期.bas:420`）
- 明細の ID は、どこからも指されていない。このため、明細は部位ごとに全件入れ替えでよく、`uid` は要らない（TateDS の部材キーは `tateds_part_key` で持つ）。並びは `sort_order` で送る
- 削除: 届いた部位一覧に無い `uid` は消し、その原価行も消す。片方で消した部位を、もう片方が同時に直していたら、台帳1件の競合として承認画面に出す（今の競合の単位のまま）

## (b) 競合の単位を台帳1件にしたときの承認画面

### 指摘12【中】木材の差が見えない。「Beaver版を採用」しても木材は戻らない

根拠:
- 比較の表は、名前・備考・状態・本体/金物/硝子/労務の合計・時間・更新日の6つ（`ProductConflictCell`、`Df_製品台帳同期.bas:1418-1438`）。行の差は「区分 行N 名前 数量×単価＝金額」を並べた文字だけ（`ProductConflictLineDiff`・`ProductLinesText`、`:1471-1497`）。木材は「本体 行N 部位名　樹種　立米◯万円 1×合計」の1行にしかならない
- 「Beaver版を採用」は `ApplyBeaverProduct` を呼ぶ（`:1353-1388`）。この関数は木材設定ID 付きの本体行を消さず、Beaver の wood_calc 行も取り込まない（`:1120`、`InsertCostLine` の `:1189-1196`）。このまま R-0268 を入れると、Beaver版を採用しても木材は Access のまま残る
- 競合の JSON は `tbl競合待ち` に台帳1件まるごと入る（`RecordProductConflict`、`:1323-1337`）

直し方:
- 単位は台帳1件のままでよい（部位ごとに選べるようにすると、原価行と合計の整合を保つ仕組みが別に要る）
- 比較の表に「木材」の1マスを足す。部位ごとに「部位名 樹種 立米単価 合計（明細N行）」を1行で出し、両側で違う部位に印を付ける。突き合わせは指摘2の `uid` で行う
- 行の差（txtLineDiff）では、違う部位についてだけ明細を「項目名 見付×見込み×長さ 数 余裕」で並べる。全部位を出すと長くて読めない
- `ApplyBeaverProduct` は、Beaver版の部位と明細で Access の木材の表を入れ替え、本体の木材行を `wood_set_uid` で付け直す。「Access版を採用」は今どおり PUT を送るだけで、Beaver 側が部位ごと入れ替える
- 建具データの JSON は比較に出さない（大きいため。指摘4・8）。出すのは「版（tateds_revision）が違う」ことだけ

## (c) 丸め

### 指摘5【高】受け取った側が計算し直すと、1円の差で往復する

根拠:
- Access の合計は `CCur(合計材積 × 立米単価 × 10000)` で、小数4桁の通貨型（`Ut_木材計算.bas` の `CalcWoodTotalBySettingId`）。本体行に書くときは `CLng(totalCost)` で整数にする（`ApplyWoodCostToHontai`）。VBA の `CLng`・`CCur` は銀行丸め（0.5 は偶数側）
- 明細の寸法と数は単精度（Single）で、樹種表の単価も単精度（調査 §1）。たとえば 12.3 は Single では 12.30000019 になる。Beaver の REAL（倍精度）に入る値とわずかに違う
- Beaver の単価は整数だけ。`validateTateguUnitCosts` は小数の unit_cost を 400 にする（`tategu_items.php:63-71`）。画面は `Math.round`（0.5 は切り上げ）で整数にしている（`ProductLedgerModal.tsx:197-198`）
- 同期の受け取りと変更の検知: Access は `修正日 > last_synced_at` を「Access で直した」とみなす（`ClassifySyncState`、`Df_Beaver連携.bas:1817-`）。台帳を変える経路はどれも `MarkProductChanged` で修正日を Now() にしてキューに積む（`Df_製品台帳同期.bas:243-252`）。Beaver では、書き込むと `recalcTateguCost` が updated_at を進める（`tategu_items.php:287-306`）
- このため、片方が取り込みのあとで合計を計算し直し、その結果を保存して変更の印を付けると、銀行丸めと四捨五入の違いや単精度の誤差で1円ずれる。ずれた側が送り返すので、往復が止まらない

直し方:
- 受け取った側は計算し直さない。部位の合計（円・整数）を部位の行に `amount` として持ち、同期ではその値をそのまま運ぶ。計算するのは、その部位を人が直したときだけ
- 計算の決まりを両側で一つにする: 倍精度で `Σ(材積×数) × 単価 × 10000` を出し、最後に1回だけ四捨五入（0.5 は切り上げ）。Access は `CLng`・`CCur` をやめて `Int(x + 0.5)` にする（労務などで使っている `RoundHalfUp2` と同じ考え方）
- Access の明細の寸法・数・余裕、樹種表の単価の列を倍精度に変える（migration）。単精度のままだと、境目の値で両側の結果が分かれる
- 受け入れ条件に「同じ部位を両側で計算した値が同じ」テストを入れる。題材は調査 §3 の代表10件（5637 の 11,084 円など）と、x.5 円ちょうどになる作り物

## (d) 樹種表の同期と名前の写し

### 指摘15【中】樹種の ID の対応と、名前を変えたときの波及

根拠:
- Access の部位は樹種を名前の写し（`樹種名`）で持ち、画面を開くときに名前で樹種表を引き直している（調査 §1・§2）。案は `species_id` を足し、名前は表示用に残す
- 原価行の名前は「部位名　樹種名　立米◯万円」（`ApplyWoodCostToHontai`）。名前の写しを樹種表から作り直すと、樹種名を1つ変えただけで、その樹種を使う全台帳の原価行の名前が変わる。そのたびに updated_at が進み、全件が同期に乗る
- 樹種表には修正日も同期の印も無い（調査 §1 の列）

直し方:
- 樹種表は Access だけで直し、Beaver へは片方向で送る（5行しかなく、使い道は単価を最初に入れることだけ）。両方向にすると、樹種そのものにも ID の対応と競合の仕組みが要る。それに見合う使い道が無い
- 部位には `species_id` と、選んだ時点の `species_name`（写し）を持つ。樹種表を直しても、部位と原価行には波及させない（単価も同じ。立米単価は「選んだときに入る値」で、あとから樹種表を直しても変えない）
- 樹種は消さず、`disabled` で使えなくするだけにする（部位から参照されるため）
- 初回: 部位の `樹種名` を樹種表の名前と完全一致で引いて species_id を入れる。引けない名前は species_id を空にし、名前だけ残す

### 指摘17【低】明細の species_id は持たない

根拠: 計算は部位の単価1つで、行の樹種IDは使われない（調査 §2、`Ut_木材計算.bas`）。137行中20行が空。Access で樹種を選ぶと、別の部位も含めて製品の全明細の樹種IDが書き換わる（`WoodForm_JushuChange`、調査 §2 の手順3）。同期に乗せると、触っていない部位まで変わったように見える。

直し方: 明細の `species_id` は Beaver に作らず、同期でも送らない。Access の列は残してよい（使わない）。

## (e) 既存データの初回の扱い

### 指摘1【高】「数量1」で作り直すと、本体数量 2・3 の行の原価が減る

根拠:
- 案は「部位1つにつき原価の行が1つ、数量1、単価＝金額＝計算した合計」（R-0268 の「原価の行とのつながり」）
- 実データでは、本体数量を枚数として使っている。5669 は数量2・単価20,382・金額40,764、5658 は数量3・金額23,811（調査 §3）
- Access の反映は、更新のときに数量を触らない（`ApplyWoodCostToHontai` の UPDATE は本体名・単価・金額だけ）。案のまま自動で作り直すと、数量が1に戻り、原価が 1/2・1/3 になる

直し方:
- 原価行の数量は人が決める値とし、作り直すときも残す。単価だけを部位の合計にし、金額＝数量×単価
- 原価行を直接は直せない（今の決まり）ので、数量を変える欄を部位の枠（「枚数」）に置く。Access の本体行の数量とは、その原価行の quantity として同期する
- 初回は今の本体数量をそのまま引き継ぐ

### 指摘10【中】共有設定19行と、設定ID空の21行

根拠:
- 同じ設定を複数の製品が指している（設定 1・2・4、8、15、18）。設定の建具№と明細の建具№が合わない明細が16行あり、設定1は明細が2製品分重なって合計が倍になっている（調査 §3「実データの不整合」）
- 部位は `tategu_item_id` で1台帳に属する形なので、共有はそのまま持ち込めない
- 5628〜5634 の6製品は、明細があるのに設定も本体の木材行も無い（反映前）

直し方（Access 側の移行スクリプトで、Beaver へ送る前に行う）:
- 共有の解消: (製品, 設定) の組ごとに設定を複製し、その製品専用の設定にする。明細は「建具№がその製品で、設定IDが元の設定」の行を新しい設定へ移す。その製品の明細が無いとき（開発版の複製で本体行だけ共有した場合）は、元の設定の明細を写す
- 共有を解消すると、設定1のような倍の合計が正しい値に戻る。19行の金額が変わるので、本番で実行する前に「本体行の今の金額」と「計算し直した金額」の対照表を晴樹さんに見てもらう。自動で原価に入れる方式にすると、この差は初回に必ず表に出る
- 本体数量が1以外の行は、指摘1のとおり数量を残す。対照表では単価の差として見せる
- 設定ID空の21行は、製品ごとに部位「（未反映）」を1つ作って入れる。単価は明細の樹種IDから取り、取れなければ 0 にする。単価が0なら原価行の金額も0なので、原価は変わらない。消すか入れるかは晴樹さんに確かめる。既定は「作って単価0」
- 明細が無い設定（3・4）と、名前が空・金額0の本体行は、部位を作ったうえで対照表に「空」と出す
- 手順: 退避 → dry-run（対照表）→ 晴樹さんの確認 → 実行 → 件数と合計の確認。R-0200 の初回と同じ

## (f) 複製

### 指摘9【中】Beaver の引用も Access の複製も、木材をきちんと写していない

根拠:
- Beaver の引用（R-0250）は、wood_calc の原価行を `source: 'manual'` に変えて写す（`frontend/src/lib/ledgerClone.ts:41`）。R-0268 で部位も写して原価行を作り直すと、手入力に変わった行と作り直した行で二重に数える。原価行の保存は `PUT /tategu-items/{id}/cost-lines` で、wood_calc の行は新しく作らない（`tategu_items.php:515-521`）。そのため「wood_calc のまま写す」だけでは消えてしまう
- Access の開発版の複製は、本体行の木材設定IDをそのまま写す（共有になる）。本番版は明細だけを元の設定IDのまま写す（調査 §2「製品の複製との関係」）。どちらも、指摘10 の共有が増え続ける原因になる。設定ごと写す `CopyWoodSettingFrom`（`Evt_木材原価.bas:271-288`）はあるが、どこからも呼ばれていない。しかもこの関数は、新しい設定IDを `DMax("ID", …, 建具№)` で引いている

直し方:
- Beaver: 引用の下書きに部位と明細を含め、新しい `uid` を振って作る。wood_calc の原価行は写さず、作った部位から作らせる（`ledgerClone.ts` の manual への変換をやめる）
- Access: 複製（`DuplicateTateguRecord`）から、部位ごとに `CopyWoodSettingFrom` を呼ぶ。本体の木材行は新しい設定IDへ付け替え、明細だけを写す処理は外す。新しい ID は `SELECT @@IDENTITY` で取る
- TateDS の建具 ID（tateds_design_id）は複製先にも写してよい（同じ設計から作った印）。同じ建具をもう一度貼り付けたときの入れ替えは、その台帳の中だけで行う

## (g) 建具データの JSON と WAF、Access の長いテキスト

### 指摘4【高】台帳の PUT に入れると、WAF と Access の SQL の上限に当たる

根拠:
- ConoHa の WAF は大きな JSON の POST を PHP の手前で 403 にする。実データでは約121KBまで通り、約127KB以上で弾かれた。大きさだけでなく中身にも反応する（2026-10-29 の記録）。Access が区切って送っているのは初回の bulk だけ（`PackBulkBatches`、64KB、`Df_製品台帳同期.bas:1635-1650`）。それでも「1件で上限を超えるものはその1件だけで1束」にしている
- ふだんの同期は台帳1件を1回の PUT で送る（`SendProductQueueRow`、`:496-563`）。403 は `HandleFailedStatus` で 4xx として `failed_permanent` になる（`:577-579`）。WAF の判定（`IsWafBlock`）は bulk にしか無い。建具データの大きい台帳は、理由が分からないまま二度と送られなくなる
- 送る JSON は送るときに作る（`BuildProductPayload`）。文字のエスケープ `EscapeJsonStringLocal` と、受け取るときの `DecodeJsonUnicode` は、1文字ごとに `result = result & …` で文字列をつなぐ（`Df_Beaver連携.bas:5347-`、`:4363-4420`）。長さの2乗で遅くなるので、数十KBの JSON では1件ごとに秒単位でかかりうる
- Access は取り込みと競合の記録を、値を SQL に埋め込んだ `db.Execute` で書いている（`ApplyBeaverProduct` の INSERT/UPDATE、`RecordProductConflict` の `SqlTextLit(beaverJson)`、`:1323-1337`）。Access の SQL 文は約64,000文字までなので、建具データを含む JSON はここで失敗する。競合の記録が失敗すると、競合そのものが残らない

直し方（今ある製品図の同期と同じ形にする）:
- 建具データは台帳の同期 JSON に入れない。`GET/PUT /tategu-items/{id}/design` を別に作り、台帳の同期 JSON には `design_sha256` と `tateds_revision` だけを載せる。相手は「覚えているハッシュと違うときだけ取りに行く・送る」。この形は製品図で動いている（R-0200 の「製品図」、`tategu_items.php:195-231`、`PushDrawingIfChanged`・`PullDrawingIfChanged`）
- 送り方は multipart（`file` に JSON を入れる）。製品図の multipart は 2.9MB まで WAF を通っている。上限（たとえば 2MB）を決め、超えたら送らずに警告する
- Access では、建具データを DAO の Recordset でフィールドに代入して書く（SQL に埋め込まない）。競合の記録 `tbl競合待ち` にも建具データは入れない（台帳の JSON に入るのはハッシュだけなので自然にそうなる）
- `tateds_imported_lines`（取り込んだときの明細の控え）は、JSON ではなく明細のハッシュ（`tateds_imported_hash`）にする。「手で直した」の判定には、ハッシュを比べるだけで足りる
- 製品の PUT で 403 かつ HTML が返ったときも、`IsWafBlock` で見分け、WAF のメッセージを出す（建具データを外しても、台帳1件が大きくなることはありうる）

### 指摘8【中】建具データは台帳に1つ。部位ごとに持たない

根拠: 案は `tateds_design_id`・`tateds_revision`・`tateds_design_json` を部位の列にしている。一方で、TateDS の1枚の建具は樹種ごとに部位を分ける（框まわり＝ひのき、腰板＝杉。R-0268「晴樹さんの決定」）。1つの設計の JSON が部位の数だけ重なり、片方だけ新しくなるとずれる。

直し方: 建具データ（design_id・revision・JSON）は台帳1件に1つ持ち（`tategu_items` の列か、1対1の表）、部位には `tateds_design_id` だけを残す（どの設計から来たかの印）。1台帳に複数の設計を貼ることを許すなら、`(tategu_item_id, design_id)` の表にする。

## (h) 自動保存と、開いている画面の楽観ロック

### 指摘3【高】製品台帳の画面には楽観ロックが無い

根拠:
- 台帳の保存は `PUT /tategu-items/{id}` → `PUT …/cost-lines` → `PUT …/labor-lines` の3回に分かれている（`ProductLedgerModal.tsx:190-211`、`TateguItemDetail.tsx:128-134`、`api/tateguItems.ts:52-82`）。どれも expected_updated_at を送らず、API も確かめない（`tategu_items.php:500-641`）。得意先（`customers.php:210-234` の stale_customer）や伝票（R-0264 の stale_voucher）にはある
- Access からの PUT は `base_synced_at` で確かめ、Beaver が新しければ 409 になる（`tategu_items.php:172-184`）。逆向き（Beaver の古い画面が、Access から届いた新しい内容を上書きする）を防ぐものは無い
- 今は「保存」ボタンを押したときだけの問題だが、案は「入力したら自動保存」。画面を開いている時間のどこかで Access の同期が届くと、次の自動保存が Access の変更を黙って消す。その結果は Access の変更として送り返されないので、Access 側も気づかない

直し方:
- 台帳の書き込みのすべて（親・原価行・労務行・新しい木材の口）に `expected_updated_at` を付け、違えば 409 `stale_product` と今の台帳を返す。得意先・伝票と同じ形
- 木材の自動保存は、部位1つ単位の口（`PUT /tategu-items/{id}/wood-sets/{uid}`）にする。中で部位・明細・その原価行・台帳の合計と updated_at を1回のトランザクションで書く。台帳全体を毎回送らない
- 画面は 409 を受けたら入力を止め、「Access で直されました。読み直します」と出して読み直す（未保存の入力は控えとして見せる）
- Access 側: 木材の画面は `acDialog`（モーダル）で開く（`OpenWoodCostForm`、調査 §2）。開いている間に自動同期で同じ台帳を取り込むと、指摘2の隠し欄の設定IDが指す行が消える。木材の画面を開いている台帳は、取り込みを飛ばして次の同期に回す（または競合として扱う）

### 指摘13【中】access-link が updated_at を進めるので、R-0264 と同じことが台帳でも起きる

根拠: 台帳の access-link は `updated_at = CURRENT_TIMESTAMP` を書く（`tategu_items.php:192`）。R-0264 は、伝票の access-link では進めないように直し、得意先と台帳は「画面に出る番号そのものを書き換えるので今のまま」とした（`docs/requests_log.md:731-` の R-0264）。Beaver で台帳を作り、木材を自動保存で入力している最中に Access が番号を振ると、指摘3のロックを入れた場合、次の保存が必ず 409 になる。

直し方: 台帳のロックは updated_at ではなく、中身の版（`content_version`。access-link と製品図では進めない）で見る。または、409 の応答で違いが `code` だけなら、画面は番号を差し替えて保存をやり直す。どちらかを決めてから実装する。

### 指摘11【中】秒の単位と offset のページ送りで取りこぼす

根拠:
- Access の取り込みは、受け取った最大の updated_at を基準時刻にし、次は `updated_at > since` で引く（`SyncProductsFromBeaver`、`Df_製品台帳同期.bas:952` に「同じ秒の取りこぼしが問題になったら」という ponytail の注記がある）。基準と同じ秒に Beaver で直された台帳は、次から引かれない
- ページ送りは `ORDER BY updated_at, id LIMIT ? OFFSET ?`（`tategu_items.php:137`）。読んでいる途中で前のページの台帳が直されると、その台帳が後ろへ移るぶん、境目の1件が飛ばされる。飛ばされた台帳の updated_at は基準時刻より古いので、二度と引かれない
- Access からの PUT の競合判定も秒単位の文字列比較（`$updated > $base`、`tategu_items.php:178`）。同期と同じ秒の Beaver の変更は競合にならず、上書きされる
- 自動保存で台帳の更新が細かく増えると、どれも起きやすくなる

直し方: GET の応答に `server_time`（読んだ時刻）を入れ、Access はそれを基準時刻にする。`/sync/changes` は既に返している（`sync.php:62`）。ページ送りは offset ではなく `(updated_at, id)` より後ろ、で続きを引く（keyset）。updated_at をミリ秒にするのが根本だが、範囲が広いので、まずこの2つでよい。

## (i) ほかに気づいた点

### 指摘6【高】両側を同時に入れ替えないと、wood_calc の行が二重になるか消える

根拠:
- 今の Beaver は、Access から届いた cost_lines で wood_calc の行も含めて全件入れ替える（`tategu_items.php:75`）
- 今の Access は、Beaver の wood_calc の行を取り込まず、自分の木材の本体行を残す（`Df_製品台帳同期.bas:1120`、`:1189-1196`）
- Beaver だけ先に R-0268 にすると: Beaver で作った部位の原価行は Access に入らない。Access が台帳を送ると、Beaver の wood_calc の行が Access の行（wood_set_uid なし）で入れ替わり、部位と原価行の対応が切れる。逆に Access だけ先だと、Beaver は wood_sets のキーを知らずに無視する

直し方:
- Beaver の PUT/POST/bulk は、`wood_sets` のキーがあるときだけ部位を入れ替える（`cost_lines` と同じく `array_key_exists`）。キーが無い（古い Access）ときは、wood_calc の原価行と部位をどちらも残す
- Beaver の画面で木材を編集できるようにするのは、新しい Access が動いていると確かめてから（設定のフラグで開ける）。それまでは今どおり読み取りだけにする
- 入れ替える順番: Beaver（受け取れるようにするだけ）→ Access → Beaver の編集を開ける。R-0200 と同じく dodai-back と時期を決める

### 指摘7【中】伝票のモーダルで自動保存すると、明細に入る原価がずれる

根拠: R-0200 の「保存したら、その伝票のその明細だけ原価に反映する」は、モーダルの［保存］で、画面が持っている `costLines` の合計（`totals.body`）を明細に渡している（`ProductLedgerModal.tsx:145-170`、`:212-227`。明細側は `LineItemRow.tsx:186-209` の `handleTateguSelect`）。木材を自動保存でサーバーに書いても、モーダルの `costLines` の wood_calc の行が古いままなら、明細には古い本体原価が入る。保存せずに閉じると、台帳の原価は変わる（Access にも行く）のに、明細は変わらない。

直し方: 木材の自動保存の応答で、台帳の wood_calc の原価行と cost_body を返し、モーダルの状態に入れる。明細に渡す値は、保存のあとに台帳を読み直したサーバーの値にする（`applied` を画面の計算で作らない）。閉じるときに「台帳の原価が変わりました。この明細に入れますか」を出すかどうかは晴樹さんに確かめる。

### 指摘14【中】Access の貼り付けが製品の全部位の明細を消す

根拠: `PasteWoodLines` は「その製品の木材明細を全部消して入れ直し、木材設定IDは0」（調査 §2 の手順5、§5）。部位を分ける運用（框まわり／腰板）にすると、腰板を貼り付けたときに框まわりの明細も消える。その状態が同期で Beaver にも届く。案の「貼り付けはその部位の中だけ」は Beaver の画面の話で、Access 側の直しが書かれていない。

直し方: Access の貼り付けも、開いている部位（設定ID）の明細だけを入れ替える。あわせて、新しい設定IDを `(建具№, 部位名)` で引き直す処理（`WoodForm_Apply`、調査 §2「反映の処理」の3）を `@@IDENTITY` に変える。部位を分けると同じ部位名が並びやすく、取り違えが起きる。

### 指摘16【低】原価行の名前の形と長さ

根拠: Access の名前は `Format(単価, "0.##")` のため「立米60.万円」と末尾に点が残る（`ApplyWoodCostToHontai`、調査 §2）。Beaver が別の形で名前を作ると、どちらが作り直したかで名前が変わり、競合の比較で差に見える。Access の本体名は30文字までで、超えると取り込みのときに切り詰めて警告を出す（`InsertCostLine`、`Df_製品台帳同期.bas:1209-1212`）。部位名（30文字）＋樹種名＋「立米◯万円」は30文字を超えうる。

直し方: 名前の作り方を1つの決まりにして両側で同じにし、末尾の点は出さない（初回に1回だけ名前が変わる）。部位名は Beaver でも30文字まで、原価行の名前は30文字で切る（両側同じ）。

### 指摘18【低】数0の行を外すのは Beaver の画面だけ

根拠: 案は「数0の行は保存時に外す」。実データでは、数0の行が137行中56行ある（テンプレートの残り。調査 §3）。同期で受け取ったときに外すと、受け取っただけで中身が変わり、updated_at が進んで送り返される。

直し方: 外すのは Beaver の画面で人が保存したときだけ。同期で受け取った行はそのまま入れる。

## まとめ（案に足すべき決めごと）

1. 部位に `uid`。明細は部位ごとに全件入れ替え。原価行・Access 本体行は `uid` で付ける
2. 部位に合計 `amount` と枚数（原価行の数量）を持ち、受け取った側は計算し直さない。四捨五入の決まりを1つにし、Access の単精度の列を倍精度にする
3. 建具データは台帳に1つ。製品図と同じく、別の口・ハッシュ・multipart で送る。Access は Recordset で書く
4. 台帳の書き込みすべてに楽観ロック。木材は部位単位の口で自動保存。access-link との兼ね合いを先に決める
5. 樹種表は Access → Beaver の片方向。名前と単価は部位に写して、波及させない
6. 初回は Access 側で共有を解消し、金額の対照表を晴樹さんに見せてから実行
7. 複製は両側とも部位ごと深く写す。Beaver の「wood_calc を manual に」はやめる
8. 入れ替えの順番を決め、`wood_sets` のキーが無い PUT では木材を触らない
