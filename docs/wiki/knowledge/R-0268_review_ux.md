## 重さ「高」

### H1. 「自動保存」と、画面の保存ボタンの食い違い

- 根拠: 製品台帳の画面（`TateguItemDetail`）も伝票から開くモーダル（`ProductLedgerModal`）も、今は［保存］／［保存して明細へ反映］を押したときにまとめて API へ送る作り。材料費・労務費の表は画面の state を書き換えるだけで、入力のたびに保存はしていない。モーダルは「この伝票の明細だけに原価を反映」する作りで、キャンセルすれば台帳も伝票も変わらない。新規作成（`mode='create'`）と引用（R-0250）のときは台帳の ID がまだ無く、木材だけ先にサーバーへ保存することができない。
- 案の「入力したら自動保存し、原価の行も更新」を木材の欄だけサーバーへ即保存する意味に取ると、次のことが起きる。
  - モーダルでキャンセルしても木材と wood_calc 行だけ台帳に残り、伝票の明細の原価は古いまま。
  - 新規・引用の台帳では保存先が無い。
  - 1 打鍵ごとに台帳の `updated_at` が進み、Access との競合（台帳1件単位の 409）が起きやすくなる。
- 提案: 晴樹さんの「反映ボタンをなくし、入力したら自動で原価に入れる」は、画面の中で即時に原価へ入れる、と解釈する。木材の明細を1つ直すたびに、同じ画面の材料費の表の wood_calc 行と右のサマリー（モーダルの製造原価）がすぐ変わる。サーバーへの保存は今の［保存］とまとめて1回にする（台帳本体・材料費・労務費・木材を同じ保存で送る。木材は `PUT /tategu-items/{id}/wood` のような1つの窓口で、部位・明細・wood_calc 行を同じトランザクションで作り直す）。これで Access の「反映忘れ」（6 製品に残っている）は Beaver では起きなくなる。
- あわせて: モーダルは背景のクリックで閉じる（`overlayStyle` の `onClick={onClose}`）。木材の入力が加わると打ち込む量が増えるので、変更があるときは背景クリックで閉じない、または確認を出す。

### H2. 木材の行の「数量」を固定の 1 にすると、既存の使い方が壊れる

- 根拠: Access では反映が本体行の数量に触れない（UPDATE は名前・単価・金額だけ）。晴樹さんは本体数量を 2 や 3 にして「1 枚分の木材 × 枚数」にしている（5669 は数量 2 で 40,764 円、5658 は数量 3 で 23,811 円）。案は「数量1、直接は直せない」。このままだと、同期のたびか Beaver で直したときに、これらの原価が 1/2・1/3 になる。
- 提案: wood_calc 行のうち「数量」だけは直せるようにする（名前・単価・金額は今どおりロック）。Beaver の再計算でも数量は残す。TateDS から取り込むときは、建具データの `count`（建具の枚数）を数量の初期値にする。Access 側も数量を触らない今の動きのままでよい。

### H3. 既存データを取り込むだけで原価が変わらないようにする

- 根拠: 木材の本体行 44 行のうち 19 行で、金額が「明細の材積合計 × 単価」の再計算と合わない（複製による設定の共有で明細が二重、数量 1 以外、反映し忘れ）。自動で原価に入れる作りのまま初回取り込みで再計算すると、晴樹さんが出した見積の原価が黙って変わる。
- 提案:
  - 初回取り込みでは wood_calc 行の金額を書き換えない。部位の枠には「明細から計算した合計」と「原価の行の金額」を並べ、違うときだけ「Access で反映した金額と違います（原価は ¥◯◯ のまま）」と出す。その部位の明細か単価を Beaver で1回でも直したら、計算した値に切り替える。
  - 共有された設定（設定 1・2・4・8・15・18）は、指している製品ごとに部位を複製して持たせる。明細は、明細の建具№がその製品と一致する行を付ける。一致する行が無い製品には設定元の明細を写す。こうすると設定 1 の「24 行で合計が倍」は製品ごとに 12 行へ分かれる。
  - 設定 ID が空の明細（21 行、5628〜5634 の 6 製品）は「未反映」という部位にまとめて入れ、樹種と単価は空のまま。単価が空（0）の部位は原価の行を作らず、枠に「樹種を選ぶと原価に入ります」と出す。見積用の 6 製品の原価が勝手に増えない。
  - 明細の無い設定（3 と 4）と、金額 0・名前空の本体行（8 行）は、部位として残して枠に「明細なし」と出す。消すかどうかは晴樹さんが画面で決める（質問 Q4）。

### H4. TateDS の木取りは鏡板・腰板を出していない

- 根拠: 晴樹さんの例は「框まわり＝ひのき、腰板＝杉」。TateDS の `calculateCost` はパネル・鏡板を面積で計算し、`depth: 0` で出す（`パネル${index}(wood)` と「鏡板・ガラス」）。`buildKidoriRows` は `depth > 0` だけを残すので、木の板は木取り表に載らない。板の厚みの項目も無い。フラッシュ戸の縁材も、木取りボタンから引数が渡らず載らない。今のままでは、腰板の部位がいつも空になる。
- 提案: TateDS の材料リストに木のパネルを入れる（材質 `wood` のパネルだけ。ガラス・障子・紙は入れない）。厚みは TateDS に「板厚」を足すか、無ければ既定値（Access のテンプレートの特殊板と同じ 15mm）で出す。「鏡板・ガラス」（パネル材質の指定が無い建具）は木かガラスか分からないので出さず、Beaver の枠に「TateDS で板の材質が未指定」と出す。

## 重さ「中」

### M1. キーボードの動き（Tab・Enter・末尾の空の行）

- 根拠: 今の空の行（`CostBlankRow`・`LaborBlankRow`）は、最後の数値欄で Tab → 行を確定して新しい空の行の先頭へ、名称が空のまま Tab → 次の区分の空の行へ、入力ありの Enter → 確定して新しい空の行へ（R-0266）、移った先を見えるまでスクロール（R-0262）、IME 変換中は横取りしない（R-0232）。Access のデータシートでは Enter で右のセルへ進むので、晴樹さんは寸法を打つたびに Enter を押す可能性が高い。
- 一方、`TateguItemDetail` は全体が `<form onSubmit>` で、入力済みの行の Enter は何もしていない。コードを見るかぎり、入力済みの行で Enter を押すとフォームが送信され、保存して前の画面へ戻る（ブラウザの暗黙の送信）。明細の数値欄が 6 列ある木材の表では、この誤操作がよく起きそう。
- 提案（木材の表）:
  - Tab の順: 部位の枠（部位名 → 樹種 → 立米単価）→ 明細の1行目（項目名 → 見付 → 見込み → 長さ → 数 → 余裕）→ 次の行 … → 末尾の空の行 → ［＋ 部位を追加］。
  - 末尾の空の行: 余裕で Tab、または入力ありで Enter → 行を確定し、新しい空の行の項目名へ（R-0262 のスクロール付き）。項目名が空のまま Tab → 次の部位の部位名へ（材料費の「次の区分へ」と同じ考え方）。空のまま Enter → 何もしない。
  - 入力済みの行の Enter は「右のセルへ進む。行の最後なら次の行の項目名へ」にし、フォームの送信は止める。Access と同じ動きになる。材料費・労務費の表にも同じ送信の問題があるので、木材の実装のときに一緒に止める（別要望にするかは指揮役の判断）。
  - 空の行の余裕は、直前の行の余裕を薄く初期値として出す（テンプレートでも 3〜6mm が大半）。「入力あり」の判定には初期値の余裕を数えない（今の空の行が数量 1 を数えないのと同じ）。
- 入力途中の行の扱い: H1 の提案どおり画面の保存でまとめて送る形なら、空の行の打ちかけは行から出たとき（blur）に確定し、［保存］を押すと blur が先に起きるので失われない。打ちかけのまま画面を離れる場合だけ消える（今の材料費と同じ）。

### M2. 数 0 の行は「保存時に外す」と、テンプレートの入力が途中で消える

- 根拠: 137 行中 56 行が数 0 で、テンプレートの 12 行を入れてから使う行だけ本数を入れる使い方。サーバーへの保存（自動でも手動でも）のたびに数 0 の行を外すと、テンプレートを入れて本数を順に入れている途中で、まだ入れていない行が消えるおそれがある。
- 提案: ひな形は、数を入れるまで「候補の行」（薄い表示、保存されない）として出す。数を入れた行だけが本当の行になる。保存時に外すのは、既存データで数が 0 の行だけ。既存の 56 行は初回取り込みで外さず、枠の下に「数 0 の行 ◯件（表示）」とたたんで見せる。外すのは晴樹さんがその部位を直して保存したとき。

### M3. ひな形の中身

- 根拠: Access のテンプレートは 12 行で、框戸・格子・組子が混ざっている（框・上桟・中桟・下桟・束・格子タテ・格子ヨコ・額・隅丸・組子縦・組子横・特殊板）。案は「框戸・格子・枠」の 3 種と書くが、中身が決まっていない。
- 提案（既定値は Access のテンプレートの値を使う）:
  - 框戸: 框 45×30×2000 数2 / 上桟 70×30×900 / 中桟 40×30×900 / 下桟 70×30×900 / 束 25×30×2000（余裕 6）
  - 格子: 格子タテ 18×15×2000 / 格子ヨコ 18×15×900（余裕 5）、組子縦 8×15×2000 / 組子横 8×15×900（余裕 3）
  - 枠: 実例 5648 に合わせ 框（たて枠）150×100×3000 数2 / 鴨居 150×100×2000 / 戸当たり 20×20×3000（余裕 5）
  - 額・隅丸・特殊板は框戸の候補の末尾に出す。どれも M2 の候補の行として入れる。ひな形の中身はコードに置き、マスタ画面は作らない（必要になったら足す）。

### M4. 木材の欄の置き場所

- 根拠: wood_calc 行は材料費の表の「本体」に並ぶが、ロックされていて、そこから木材の明細へ行く手段が無い。Access は本体の行を選んでからボタンを押す作りで、2 つ目の部位を足すのが分かりにくかった（調査 6 章）。
- 提案:
  - 「木材」の欄は材料費明細のすぐ下（労務費の上）に置く。製品台帳の画面とモーダルで同じ部品を使う（今の `TateguCostLinesPanel` と同じやり方）。
  - 材料費の表の wood_calc 行には「木材で直す」のリンクを付け、押すとその部位の枠へスクロールして部位名にフォーカスする。ロックの理由が画面で分かる。
  - 部位の枠は1行の見出し（部位名・樹種・立米単価・樹種の単価（違うときだけ薄く）・合計）と明細の表。明細の表に読み取り専用の「材積」列を足すと、桁違い（1.5mm と 15mm の打ち間違い）に気づける。
  - ［＋ 部位を追加］とひな形のボタンは、最後の部位の下に1か所だけ。部位が無い台帳では、木材の欄はボタン1行だけにたたむ（多くの台帳は木材を使わない）。

### M5. TateDS の寸法と Beaver の式のずれ

- 根拠: Beaver・Access の式は (見付+余裕)×(見込み+余裕)×(長さ+100)。TateDS の木取り寸法は、取り幅 = 幅+5、取り厚 = 見込み+3、取り長 = 長さ+ほぞ×2+50 で、`length` はほぞを含まない。取り寸法を渡すと余裕と +100 が二重に足される。仕上がり寸法をそのまま渡すと、ほぞの分が抜ける。
- 提案: クリップボードには仕上がりの見付・見込みと「長さ+ほぞ×2」を入れ、余裕は Beaver の部位の既定値（または TateDS の幅側の余裕 5）を入れる。長さの +100 は Beaver の `length_allowance_mm` に任せる。TateDS の材積・単価（立米 80 万円・歩留まり 10%）は使わない。

### M6. TateDS の樹種と Access の樹種表の対応

- 根拠: TateDS の樹種は hinoki・sugi・nara・keyaki・walnut の 5 つ（任意項目）。Access は ヒバ・杉・ひのき・ぼろい杉・杉(別)。杉の系統が 3 つあり、TateDS の sugi はどれにも当たりうる。nara・keyaki・walnut は Access に無い。ヒバは TateDS に無い。
- 提案:
  - 初期の対応: ひのき → hinoki、杉 → sugi。ぼろい杉・杉(別) にも sugi を入れてよい（同じキーを複数の樹種に付けてよい）。ヒバは空。
  - 取り込みでは、キーが合う樹種のうち表示順が最初のもの（杉）を選ぶ。部位の樹種を手で「ぼろい杉」に変えたら、取り込み直しでもその選択を残す（部位の樹種のキーが同じ sugi なら変えない）。
  - 対応が無い樹種（nara など）と、TateDS で樹種の指定が無い部材は、縦框の樹種に寄せる。縦框も未指定なら樹種が空の部位にし、H3 と同じく原価に入れず「樹種を選んでください」と出す。
  - 樹種表の画面（Access の「樹種マスタ」ボタンは TODO のまま）に TateDS の対応の列を足すかは Q5。

### M7. 樹種が混ざる建具を部位に分ける規則

- 提案: TateDS の部材グループ（stile・topRail・bottomRail・middleRail・tsuka・kumiko・panel）を樹種でまとめ、樹種1つにつき部位1つ。部位名の初期値は中身で決める。框・桟・束を含む → 「框まわり」、パネルだけ → 「腰板」、組子だけ → 「組子」、それ以外 → 樹種名。部位名・単価は取り込み後に手で直せて、取り込み直しでも残す。部位のキーは「建具 ID + TateDS の樹種キー」。

### M8. 取り込み直しと「手で直した」印

- 提案:
  - 同じ建具 ID のものを貼り付けたら、まず変更の一覧を出す（部位の追加・削除、明細の増減、手で直した部位）。［入れ替える］で実行し、手で直した部位には「手で直した明細は TateDS の内容で上書きされます」と書く。版（`updatedAt`）が同じなら「変更はありません」で終わる。
  - 「手で直した」は明細（項目名・寸法・数・余裕）だけを比べる。部位名・樹種・単価・数量は手で決めるものとして比べず、取り込み直しでも残す。
  - TateDS で樹種を変えた（sugi → hinoki）ときは部位のキーが変わる。一覧で「杉の部位を消して、ひのきの部位を作る」と見せる。
  - 1 つの台帳に TateDS の建具を 2 つ以上つないでよい（建具 ID ごとに部位の組ができる）。

### M9. クリップボードの形式

- 提案（TateDS → Beaver・Access の「材料リストをコピー」）:
  - text/plain に JSON を1つ入れる。先頭のキーで見分ける: `{"format":"tateds-materials","version":1,"designId":"<UUID>","revision":<updatedAt>,"name":..,"tag":..,"count":..,"lines":[{"partKey":"stile","name":"縦框","species":"hinoki","mitsuke":..,"mikomi":..,"length":..,"qty":..}],"design":{…}}`
  - Beaver・Access は `format` が違えば TateDS の貼り付けとして扱わず、今の TSV の貼り付け（Excel）として試す。`version` が知らない大きな数なら「TateDS が新しい形式です。Beaver の更新が要ります」と出して何も書かない。
  - Beaver 以外（メモ帳・Excel・LINE）に誤って貼った場合は、ただの長い1行の文字列になるだけで害は無い。中に価格や得意先は入らない（入れない）。気になるなら `design` を抜いて小さくする手もあるが、「TateDS で開く」に要るので入れておく。
  - Access の今の貼り付け（`PasteWoodLines`）は 6 列の TSV 前提で、JSON を貼ると「既存の明細は削除されます」の確認のあとに変な行が入る。Access の改修が入るまでは、TateDS の新しい形式を Access で貼らないよう Dodaikun に伝える。
- 提案（Beaver・Access → TateDS の「TateDS で開く」）:
  - 同じ JSON の `design` 部分だけ（`format":"tateds-design"`）を入れて TateDS を開く。TateDS の「貼り付けて開く」で読み込む。TateDS の端末に同じ建具 ID があって、そちらの `updatedAt` が新しいときは「この端末の方が新しい」と出して選ばせる。
  - Beaver と TateDS は本番で同じオリジン（door-fujita.com）なので、Beaver からは `postMessage` で渡す手もある。ただし Access はクリップボードしか使えないので、まずはクリップボード1本にそろえる。

### M10. 建具データの大きさと WAF

- 根拠: TateDS の `StoredDoor` には `thumbnail`（画像の文字列）がある。部位ごとに `tateds_design_json` を持つので、樹種が 2 つなら同じ建具データが 2 つ入る。ConoHa の WAF は大きな JSON の POST を PHP の手前で 403 にした実績がある。
- 提案: `design` からは `thumbnail` と `id`（端末ローカルの連番）を除いて送る。建具データが WAF に当たる大きさか、実データで1件測る（指揮役の確認事項）。

### M11. 複製（既存の台帳から引用）

- 根拠: `buildLedgerCloneDraft`（R-0250）は wood_calc 行を手入力の行に変えて写す。木材の部位を Beaver で持つと、このままでは複製先に部位が無く、原価の行は直せる手入力の金額として残る。Access では複製で設定を共有してしまい、片方を直すともう片方が変わっていた（調査 6 章）。
- 提案: 引用では部位・明細を新しい行として写し（共有しない）、wood_calc 行は部位から作り直す。TateDS のリンク（建具 ID・版・建具データ）も写す。R-0250 の「wood_calc 行は手入力にする」は、R-0268 で置き換える。

### M12. 原価の行の名前と丸め

- 根拠: Access の名前は `Format(単価,"0.##")` のため「立米60.万円」と末尾に点が付く。Beaver が「立米60万円」と作ると、両側で計算し直すたびに名前が入れ替わる。Beaver の API は単価に小数を許さない（`validateTateguUnitCosts` が 400）ので、丸めは必ず要る。Access の Long への代入は銀行丸め。
- 提案: 名前は「部位名　樹種名　立米60万円」（小数があるときだけ 62.5）に Access 側も直す。金額は部位ごとに円未満を四捨五入（0.5 は切り上げ）して、Access も `Int(x + 0.5)` でそろえる。既存の 44 行の名前は、その部位を直すまで今のまま。

## 重さ「低」

### L1. 部位の削除と並べ替え

- 提案: 部位の見出しの右に ▲▼ と［部位を削除］（今の `MoveButtons` と同じ見た目）。明細があるときだけ「部位『框まわり』と明細 5 行を消します」と確認する。原価の行の並びは部位の並びに合わせ、材料費の「本体」の中で手入力の行の後ろに置く。明細の行にも ▲▼ と削除を付ける（Access の行削除ボタンに当たる）。

### L2. 部位名のゆれ

- 根拠: 「本体」7、「ほんたい」4、「hontai」など。部位名はそのまま原価の行の名前になる。
- 提案: 部位名の欄に `<datalist>` で候補（本体・框まわり・腰板・枠・組子）を出す。空のときは「本体」を入れる。既存の表記は勝手に直さず、直すなら晴樹さんが画面で直す。同じ台帳での部位名の重複は ID で区別するので計算は壊れないが、原価の行で見分けがつかないため、重複したら薄く注意を出す。

### L3. 立米単価と樹種の切り替え

- 提案: 樹種を変えたら立米単価を新しい樹種の単価にする（Access と同じ）。ただし手で変えた単価（樹種の単価と違う値）があるときは上書きの前に確認する。単価が樹種と違うときの薄い表示（案どおり）で、見積ごとの手入力（ぼろい杉で 22〜45）がひと目で分かる。明細の `species_id` は保存時に部位の樹種で埋める（Access の「製品の全明細の樹種を書き換える」動きはやめてもらう）。

### L4. 読み取り専用の伝票から開いたとき

- 根拠: `LineItemRow` は `readOnly` のときモーダル（`ProductLedgerModal`）を出さない。製品台帳の画面には読み取り専用の状態が無い。
- 提案: 今のまま開かない。木材の欄のために読み取り専用のモーダルは作らない。必要なら製品台帳の画面へのリンクで足りる。

### L5. 印刷・帳票

- 根拠: 伝票の Markdown 出力（`voucherMarkdown.ts`）は台帳の材料費の行を出している。木材の明細を出す帳票は Access にも Beaver にも無い。
- 提案: 当面は出さない。wood_calc 行（部位ごとの合計）は今どおり材料費の行として出る。木取り表として印刷したいなら TateDS 側の機能（未実装の A4 印刷）にまとめる方が筋がよい（Q6）。

### L6. 他の製品から木材だけ写す

- 根拠: Access の「他の製品からコピーする」ダイアログ（`frmWoodCopyDialog`）は作られているが開けない。案にも書かれていない。
- 提案: 当面は「既存の台帳から引用」（M11 で木材も写る）で足りる。部位だけ写したい要望が出たら足す。

### L7. 計算の前提の表示

- 提案: 案どおり枠の下に1行で「材積 =（見付+余裕）×（見込み+余裕）×（長さ+100）÷10⁹。余裕は見付と見込みに足す」。長さの足し分が 100 以外の部位だけ数字を強調する。
