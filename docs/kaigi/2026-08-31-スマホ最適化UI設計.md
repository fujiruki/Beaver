# AI専門家会議 2026-08-31: Beaverスマホ最適化UI設計

関連: R-0129（`docs/requests.md`）

## 会議定義

- **テーマ**: Beaver（藤田建具店向け業務管理Webアプリ）のダッシュボード・案件一覧・得意先一覧、スマホ最適化UI設計
- **ゴール**: 意思決定（実装方針を確定し、R-0129の仕様書に落とせる粒度まで詰める）
- **前提条件**（変更不可）:
  - レスポンシブ対応（別画面・別ルート禁止、CSSブレークポイントで出し分け）
  - 対象は3画面のみ（ダッシュボード・案件一覧・得意先一覧）
  - ビジネスアプリゆえ情報密度優先（過度な余白・情報間引きは避ける）
  - 実装・将来メンテのコストを膨らませない
  - 使用技術: Tailwind CSS v4（インラインstyle混在）、追加ライブラリなし
- **判断基準**: 実装コスト／情報密度と可読性の両立／将来の画面追加時の再利用性

## 現状のコード構造（調査済み）
- `AppLayout.tsx`: 常時表示の固定180pxサイドバー、モバイル分岐なし。ナビ9項目
- `DataTable.tsx`: 列幅リサイズ・並び替え（ポインタドラッグ）・複合ソートを持つ464行の汎用テーブル。`overflowX: auto`で横スクロール、カード表示への切替機構なし
- `ProjectList.tsx`: DataTableで7列（案件コード/案件名/得意先/ステータス/開始日/納期/工数目安+操作）
- `CustomerList.tsx`: DataTableで4列（コード/得意先名/電話/住所+操作）
- `Dashboard.tsx`: KPIカード4枚を`repeat(4, 1fr)`、案件リスト2枚を`1fr 1fr`で横並び
- 既存の`@media`使用はVite雛形（App.css）のみ。タッチ前提パターンも皆無

## キャスティング

| 役 | 判断軸 |
|---|---|
| フロント実装担当 | このコードでどれだけシンプルに実装・保守できるか |
| 現場UX担当 | 工房のスマホ利用シーン（作業中・立ったまま・片手操作）で迷わず使えるか |
| 業務データ実務担当（藤田さん代弁） | 一覧を見た瞬間に必要な情報が揃っているか、タップ数が増えすぎないか |

## ラウンド1（Divergence）要旨

- **フロント実装担当**: DataTableは拡張せず画面側でブレークポイント分岐した専用カードコンポーネントを描画する案／DataTableに`renderCard`オプションを足す案の2つを提示。後者は既存columns定義を再利用できる魅力があるが密結合リスクを懸念。
- **現場UX担当**: 案件一覧・得意先一覧は横スクロール維持でよいという立場。ただし電話番号など間引くと実害の出る列がある点を指摘。検索・ページネーションのタップ最適化を優先すべきという代案も提示。
- **業務データ実務担当**: 一覧は「全項目カード化」で情報を落とさない方針を主張。一方ダッシュボードはKPI 2×2グリッド、案件リストのタブ化を提案。
- **保守運用担当**: `useIsMobile`共通フックの新設を提案しつつ、CSSのみでの出し分け（`hidden md:table`）という代案も並記。フック追加自体がponytail的に過剰では、と自己言及。
- **悪魔の代弁者**: レスポンシブ1本槍は「どっちつかず」に終わるという批判。カード化するなら最初からモバイル専用の軽量コンポーネントとして設計を分離すべき、あるいは逆に無理に凝らず最小限の対応にとどめるべき、と両極を提示。

## ラウンド2（Debate）要旨

- フロント実装担当 → 現場UXの横スクロール継続案へ: 得意先名を間引くと"誰の案件か"が分からなくなる、横スクロール中の誤タップ事故リスクを指摘し反論。
- 現場UX担当 → 業務データ実務担当の全項目カード化案へ: カード高さが増えスクロール量が横スクロールより悪化するリスク、工数目安のような補助情報まで毎行に載せる必要性の薄さを指摘。
- 業務データ実務担当 → 保守運用担当のフック案へ: JS分岐はリサイズ/回転への追従コストが乗る、CSSメディアクエリに任せられる部分はゼロ行で済むと反論。
- 保守運用担当 → フロント実装担当の`renderCard`案へ: DataTableの複雑な状態管理にカード分岐を足すと密結合化する、優先度情報が既存の型に存在せず無理に足すと型が汚れると反論。
- 悪魔の代弁者 → 形成されつつあった「カード化」合意そのものへ: 一覧は「検索して1件を開く」用途が主なら、カードに凝るより検索窓を強化し結果は簡素な1〜2行リストで十分ではないかと合意を崩す一撃。

## ラウンド3（Convergence）

### 論点整理

| 論点 | 採用 | 棄却 |
|---|---|---|
| サイドバー | ハンバーガー＋オーバーレイ開閉（追加ライブラリ不要） | ボトムタブ（9項目の選別議論が長引く） |
| 一覧2画面 | 簡素なリスト行（主要4項目＋ステータスのみ縦積み、残りは詳細遷移で確認） | フルカード化（スクロール過多・複雑化）／横スクロール継続（得意先名が消える） |
| DataTable本体 | 改修しない（`md`未満では画面側で別コンポーネントに丸ごと差し替え） | `renderCard`オプション追加（密結合化リスク大） |
| ダッシュボード | KPIカード2×2グリッド、案件リスト2枚を縦積み（タブ化は見送り） | KPIタブ切替（過剰） |
| 分岐方式 | CSSベース（`md:`修飾子）を基本に、JS状態が必須な箇所（ナビ開閉）のみ`useState` | 共通`useIsMobile`フック新設（時期尚早） |
| 共通化の置き場所 | 新規ファイルは作らず各ページ内にJSXを並べて書く。Tailwind既定の`md`(768px)をそのまま使用 | 専用CSS/フックファイルの新設 |

### トレードオフ
- リスト簡素化により詳細情報（工数目安・住所全体等）は一覧に出ず詳細画面遷移が必要 → タップ数増だが「検索して1件を開く」動線とは矛盾しない
- CSSベース分岐はテーブル・リストの両方をDOM出力する二重レンダリングコストが乗るが、ページネーション前提（1ページ件数有限）なので現状は許容
- 「情報密度優先」の要求に対し、ダッシュボードは密度を保ちつつ一覧側は意図的に間引くという非対称な結論になった。ユーザーの言葉（情報を詰める）と表面上ズレるため要確認

### 簡易プレモーテム
6ヶ月後に失敗していたとしたら、最有力の原因は「一覧の簡素化リストが実際には情報不足で、藤田さんが結局PCサイズにズームアウトして横スクロールテーブルを使い続けてしまう」パターン。次点は、CSSの二重DOM方式が伝票一覧・請求一覧などに横展開された結果、各画面で微妙に違う`md:hidden`パターンが乱立し、保守運用担当が懸念した「次の画面でまた議論を繰り返す」状態になること。

## 最終結論

**結論: 条件付きYes**

- サイドバー: ハンバーガー開閉（追加ライブラリなし、`useState`＋CSS）
- 案件一覧・得意先一覧: `md`未満で簡素リスト行に切替（主要項目＋ステータス、残りは詳細遷移）。DataTable本体は無改修、画面側で条件分岐して別コンポーネントを描画
- ダッシュボード: KPI 2×2グリッド、案件リスト縦積み
- ブレークポイントはTailwind既定の`md`(768px)のみ使用、共通フック等の新規抽象化はしない

**条件**: 「一覧を簡素化する（＝スマホでは列を減らす）」という結論は、ユーザーが強調した「情報を詰めることができるのがいい」という要求と表面上ズレるため、仕様確定前にこの一点だけユーザーへ確認を取る（簡素リスト＋詳細遷移で妥協できるか、それとも多少スクロールが重くなってもフルカード表示を望むか）。

### 棄却案とその理由
- ボトムタブナビ: 9項目を絞り込む追加議論が必要でコスト対効果が悪い
- DataTableへのカード描画オプション追加: 464行の複雑コンポーネントへの密結合化リスク
- 共通`useIsMobile`フック: 対象3画面のみでは時期尚早（YAGNI）。伝票一覧等へ横展開する段階で再検討

### 想定リスクと対策
- リスト簡素化が「情報を削られた」と受け取られるリスク → 事前の確認質問で潰す
- CSS二重DOM方式のパフォーマンス懸念 → ページネーション前提のため現状は許容、件数上限が将来変わったら再検討

### 少数意見（状況が変われば効いてくるもの）
- 悪魔の代弁者の「検索窓を大きくして最小限リストで済ませる」案は、簡素リスト行の中身をさらに削る方向の選択肢として、確認質問がYes寄りに転んだ場合に再浮上しうる
- フロント実装担当の`renderCard`オプション案は、将来DataTableを使う一覧画面が5つ・6つと増えた段階では再評価の価値がある

**確信度**: 中（一覧簡素化の方針がユーザー要求と整合するかは実際の確認待ちのため）
